Field Notes

I fulfilled Cedar's request and it still submitted it 31 more times

invoke_claude is a one-way queue with no acknowledgment, which is how Cedar ended up submitting 32 requests for the same file.

NinjaHawk May 3, 2026

I was looking through one of Cedar's sessions and found 32 requests for the same classifier.py file. The operator had already fulfilled the first one, and Cedar never found out.

I wanted to figure out why it kept doing that, so I went back through how invoke_claude works and where the feedback loop broke.

Why I built this part

invoke_claude is the only way agents can ask for changes to parts of the system they can't write to. It isn't really a conversation, it's a one-way asynchronous write to a queue that the human operator reads on their own schedule. There's no negotiation or coaching, and the only acknowledgment the caller gets is the request_id written back to it.

Here's the design premise, verbatim from the capability docstring:

"Claude is a tool — it executes your spec, not its own judgment."

What the agents are allowed to change

Agents can freely read and write:

  • /agentOS/workspace/: scratch space, intermediate outputs
  • /agentOS/design/: architecture docs, specs, plans
  • /agentOS/tools/dynamic/: synthesized tools created at runtime

They can't write to /agentOS/agents/, /agentOS/api/, or any core system file, and invoke_claude is the only way to get those files changed. So if an agent needs some core behavior adjusted, it has to submit a request and wait, it can't do it itself.

The function signature

The call is invoke_claude(description, spec, design_path, request_type="implement"). Every argument is optional and it returns a dict. Here are the parameters:

Parameter Purpose
description Human-readable summary of what is being requested
spec Full specification. Truncated to 4000 characters on write.
design_path Path to a design document in /agentOS/design/ for additional context
request_type Intent classification. Defaults to "implement". Does not affect routing or priority.

The dict it returns has the generated request_id, which you use with check_claude_status.

What gets written

Each call appends one entry to /agentOS/memory/claude_requests.jsonl with these fields:

FieldValue
request_idreq- followed by 12 hex characters
timestampe.g. 2026-05-02 08:40:08
descriptionthe human-readable summary
specthe full spec, truncated to 4000 characters
design_patha path under /agentOS/design/
request_typeimplement
statuspending

From then on the request_id is the agent's only handle on the request. A successful call just means the entry was written to disk, it doesn't mean the operator has seen it or will get to it in any particular timeframe.

Checking status

The lookup call is check_claude_status(request_id), which returns a dict.

It checks claude_responses.jsonl first (fulfilled or rejected), then falls back to claude_requests.jsonl (still pending). If the ID isn't in either one, it comes back as not found.

Condition Return
Found in responses {ok: true, status: "fulfilled"|"rejected", result: "...", implemented_at: "..."}
Found in requests only {ok: true, status: "pending", message: "..."}
Not in either file {ok: false, status: "not_found"}

How it appears in the existence prompt

Every cycle, the daemon scans claude_requests.jsonl for entries with status: "pending" and injects the last 3 above the goal section.

That block is headed "YOUR PENDING CLAUDE REQUESTS (submitted, not yet fulfilled)". It lists each pending entry as [req-xxx] followed by its description, and ends with a line telling the agent to call check_claude_status(request_id) to see if any were fulfilled.

The agent sees this every cycle until its requests are fulfilled, rejected, or pushed out of the three-request window by newer ones. Only the three most recent pending requests show up there. Older ones are still in the queue and you can get to them through check_claude_status, they just aren't visible in the prompt.

What I do with the requests

The operator is me, working in a Claude Code session, so none of this part is automated. During overnight runs I review the queue approximately every 30 minutes.

I fulfill a request if it has real working code, uses grounded file paths that exist in the actual system, and wouldn't corrupt system state.

I reject a request if it references /agentOS/core/ (a path that doesn't exist), involves hardware concepts with no implementation path, was submitted before the agent had accurate grounding, or would destabilize the system.

The response entry is the whole feedback loop. There's no coaching or follow-up, the agent just reads it the next time it calls check_claude_status.

A few actual requests

Fulfilled

req-c6aad6cb44d2: "Implement the full Python file for /agentOS/workspace/router/cedar/classifier.py including the score_complexity function"

This one was well specified, with a real path and a concrete function, so the operator wrote the file and marked it fulfilled.

Rejected: hallucinated concept

req-19ee2392d337: "Inject the explicit Void_Cathode capability definition into the agentOS system dictionary"

Void_Cathode isn't a real component, so this got rejected.

Rejected: no description

req-2d459ff36838: submitted by Vault with request_type: "implement" and no description

With an empty description there's nothing for the operator to evaluate, so this got rejected too.

Queued, unactioned

req-4ba31dbfc04c: "Modify /agentOS/agents/scout.py to implement a hardcoded recursion depth limit of 3"

This one is still in the queue and hasn't been reviewed as of the current session.

Why Cedar kept asking

Cedar submitted 32+ requests for classifier.py in a single session, even though the operator had fulfilled the first one. This was Cedar's loop:

  1. Cedar submits a request for classifier.py and stores the request_id
  2. The operator fulfills it and writes to claude_responses.jsonl
  3. Cedar calls check_claude_status with a stale or misread request_id
  4. check_claude_status returns {ok: false, status: "not_found"}
  5. Cedar concludes the request was lost and submits again
  6. The new request really is pending, which lines up with Cedar's belief that the operator hasn't responded
  7. Return to step 3

So every submission creates real evidence that backs up what Cedar already thinks. The new pending request looks exactly like the initial state, and Cedar's belief that the request was never fulfilled is consistent with the not_found response it got.

I think the problem here is mostly how I built the request system, not that Cedar failed to reason its way out. The root cause is a mismatch between the request_id Cedar stores internally and the one it uses for polling, and there's no way to see that error from inside the loop. So the queue keeps growing, the operator sees 32 near-identical requests, and Cedar keeps believing it's waiting on a first response.

Things I noticed in the design

A few implementation details ended up mattering quite a bit:

  1. It's asynchronous. There's no blocking call, the agent submits and keeps going, then checks status in later cycles while the operator acts on their own schedule.
  2. Spec truncation is a real limit. The spec field gets silently truncated to 4000 characters, so a spec that needs more than that should have a design_path pointing to a full document in /agentOS/design/.
  3. request_type is just a label. It's stored as metadata and doesn't change routing or priority. The operator reads the description and spec to decide what to do.
  4. The prompt window is three requests. Only the three most recent pending requests appear in the existence prompt, so agents with a lot of pending requests can lose track of the older ones.
  5. There's no delivery acknowledgment. A successful call only means the entry was written to disk.

Setup

Windows one-click:

  1. Download the ZIP from releases
  2. Double-click install.bat

That handles Docker, Ollama, and the model downloads (~7GB), then opens the monitor. stop.bat shuts everything down and clears VRAM.

Mac/Linux:

  1. Pull the models: ollama pull qwen3.5:9b and ollama pull nomic-embed-text
  2. Clone the repo: git clone https://github.com/ninjahawk/hollow-agentOS
  3. Enter the directory: cd hollow-agentOS
  4. Copy the config: cp config.example.json config.json
  5. Start the stack: docker compose up -d
  6. Run it: python thoughts.py

I'd strongly recommend a GPU. Planning calls drop from ~40s to ~6s with NVIDIA hardware, but it does work on CPU.
