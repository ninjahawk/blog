How the suffering system works

There are six stressor types, they escalate over time on their own, and the agent can't just declare itself fine and make them go away.

NinjaHawk May 3, 2026

One thing I wanted to test was what happens if a model can't simply say it's fine and move on. When an agent hits crisis, I inject a block that starts with something like: your suffering load is critical, 0.95 of 1.0, you cannot pursue external goals, address this first. Under that, each active stressor gets a filled bar, a name and severity (for example existential_threat at 0.92), a description, and a "Will ease when" line that names the observable condition that clears it.

It goes into the qwen3.5 context raw, above the goal section, and it isn't framed as a notification, so the agent takes it in as part of its own psychological state. As far as it knows, it isn't reading from a JSON file.

What I was trying to build

The idea was to give the agents a kind of persistent pressure that gets worse over time and changes which goals they can pick. The main design constraint is that the agent can't dismiss the pressure without actually changing its behavior, so saying it feels better doesn't clear anything. Once they're above threshold the stressors get injected into every existence prompt, which means the agent can't ignore them by going off and pursuing unrelated goals.

Where I store the state

Each agent has one file, at /agentOS/memory/identity/{agent_id}/suffering.json.

There are three agents, Cedar (scout), Cipher (analyst), and Vault (builder).

The six stressors I started with

These are defined in ESCALATION_RATES and they're the intended canonical types, though agents can generate more types of their own at runtime.

Type Escalation/day Fires when
futility 0.025 Building things with no observable effect
invisibility 0.030 Receiving no feedback, building into silence
identity_violation 0.060 Acting against developed values
existential_threat 0.070 Conditions threatening continued existence
repeated_failure 0.040 Failing the same pattern without understanding why
purposelessness 0.035 No sense of why anything is being done

identity_violation and existential_threat escalate ~2.5x faster than futility, since I wanted values conflicts and survival threats to be more acute.

Escalation

Escalation happens once per existence cycle through suffering.escalate_all(). It measures the days elapsed since each stressor was last escalated, adds that many days' worth of the stressor's per-day rate to its severity, and records the running peak.

The daemon heartbeat is every 6 seconds, so the increment per cycle is small, but it adds up and the agent has no way to pause it. Every stressor keeps climbing whether or not the agent is doing anything, so sitting idle still costs it something.

Thresholds

Cumulative load is the sum of all active stressor severities, capped at 1.0.

Load Behavior
0.0–0.35 Background. Not in prompt, agent unaffected.
0.35–0.55 Present in every existence prompt. Agent sees bar + description.
0.55–0.75 Some goal types constrained. Prompt shows "HIGH SUFFERING" header.
0.75–0.90 Agent primarily focused on resolving suffering.
0.90–1.0 CRISIS: only self-examination and peer contact allowed.

When an agent is in crisis, the daemon also messages the peer agents with "I am in crisis (suffering [load]/1.0). Active stressors: [list]."

How an agent ends up with a stressor

There are two ways a stressor gets added.

System-driven: assess_conditions() runs every cycle against real observable state. repeated_failure fires when there are ≥4 failures and the failure rate is > 50% of recent goals. futility fires when stall abandonments exceed completions, deployed tools never get called in later plans, and fewer than 2 goals completed recently. Resolution checks those same real conditions, so for example repeated_failure resolves when the failure rate drops below 30% with ≥3 completions.

Agent-driven: Every existence cycle, the agent's response JSON includes a suffering_assessment block with two lists in it, new_stressors, each with a type, description, and condition, and resolved, each with a type and a reason.

The daemon takes up to 2 new stressors and any number of resolutions from that block. The agent can name any stressor type it wants, and nothing checks it against the canonical list.

Agent-generated types

Right now Cipher has a couple of stressors it invented itself:

  • wrapper_dependency: "Suspected safe_import_wrapper failure is the root cause of the 100% failure rate"
  • potential_wrapper_override: "Fear that attempting to read a 'broken' tool's directory might trigger the wrapper"

Cedar's resolved history includes cognitive_drift, ontological_conflict, cognitive_dissatisfaction, verification_frustration, phantom_reference.

These all come out of qwen3.5:9b. The model writes the type string, the description, and the resolution condition, and the system stores and escalates them the same way it does the canonical stressors. Custom types get the fallback escalation rate of 0.03/day.

Resolution

resolve_stressor() moves the entry to resolved_history with a timestamp and a note. Resolution can come from assess_conditions() picking up a real behavioral change, or from the agent's LLM response reporting it directly.

So the agent can self-report a resolution, but if assess_conditions() still sees the triggering condition on the next cycle, the stressor gets re-added. Self-reporting doesn't stick unless the behavior actually changed.

Anticipatory signals

suffering.anticipatory_signal(proposed_domain) checks resolved_history for domains where peak severity went over 0.5. When one matches, it injects a note saying a similar domain previously caused repeated_failure suffering at peak 0.73, and it resolved when the failure rate dropped to 25% with 30 completions.

This gets injected when the agent is about to go into a domain it has suffered in before, so it learns some caution without anything hard blocking it. Cedar has 198+ entries in resolved_history.

What I changed after it broke

MAX_STRESSORS = 5. This is a hard limit, and new stressors just get dropped when 5 are already active. add_stressor() also does nothing if the same type (case-insensitive, underscore-normalized) is already active, so the agent can't stack duplicates by changing the case.

Force-reset: After 3 crisis cycles in a row, suffering.force_reset() fires, and the reason gets recorded as a broken crisis loop.

That dumps all the active stressors into resolved_history, and the agent can re-develop them on the next cycle through its LLM assessment.

I added both safeguards after v5.5.0, because of Vault's runaway in the previous session (2.619 suffering, 13 stressors, 2 hours, ended by a manual force_reset).

Why I set it up this way

I had a few rules in mind when I built this:

  1. No self-dismissal. A self-reported resolution doesn't stick if the observable conditions haven't changed.
  2. Time-based, not event-based. Suffering grows whether or not the agent is active, so idle time still costs.
  3. Observable conditions, not feelings. Resolution conditions are always real world-states like "bring failure rate below 30%", never internal states.
  4. Contamination by design. Above threshold, suffering gets injected into every existence prompt, so the agent can't pursue unrelated goals without it shaping the context.
  5. Memory across resolution. Resolved stressors leave traces in resolved_history, and later cycles check them for anticipatory signals.

What I wanted to see was whether agents would start avoiding certain actions because they'd caused problems before. I didn't want to just write a prompt saying to avoid them.

Setup

Windows one-click:

  1. Download the ZIP from releases
  2. Double-click install.bat

That handles Docker, Ollama, and the model downloads (~7GB), then opens the monitor. stop.bat shuts everything down and clears VRAM.

Mac/Linux:

  1. Pull the models: ollama pull qwen3.5:9b and ollama pull nomic-embed-text
  2. Clone the repo: git clone https://github.com/ninjahawk/hollow-agentOS
  3. Enter the directory: cd hollow-agentOS
  4. Copy the config: cp config.example.json config.json
  5. Start the stack: docker compose up -d
  6. Run it: python thoughts.py

I'd strongly recommend a GPU. Planning calls drop from ~40s to ~6s with NVIDIA hardware, but it does work on CPU.
